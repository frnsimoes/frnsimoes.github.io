A small history of modern Postgres IO

Nov 15, 2026

In 2007, Heikki Linnakangas proposed a sequential scan roadmap for Postgres. One of the problems Heikki was trying to solve was how to optmize Postgres’ shared buffers when a table was larger than shared buffers. He argued that there’s no point in spoiling shared buffers because the performance gains are minimal when the table is much larger than the buffer (say, 5 or 10 times more). Such scans also evicted other tables’ data from the buffer if there was no activity. So he proposed that, instead, big tables should reuse a small ring of buffers within shared buffers.

Luke Lonergan replied with an idea that went beyond the buffer ring: readahead inside the heap scan itself. The kernel already did readahead, but Postgres still asked for one 8 KiB page per syscall. Luke wanted Postgres to read N buffers ahead, issuing contiguous reads to the OS, which would be much larger than a single page. But Heikki was skeptical, since the OS should handle readahead anyway. At this point, Andreas Zeugswetter pointed out that doing it properly would need scatter-gather I/O, a single call that fills several buffers, and Gregory Stark went further by saying that the real win would require async I/O.

Heikki’s idea was merged in Postgres 8.3.0. In 2009, the same Greg Stark introduced prefetch with posix_fadvise for bitmap heap scans in Postgres 8.4. It also introduced effective_io_concurrency to control how aggressively Postgres prefetched pages through the OS.

In 2023, Thomas Munro opened a thread that became read streams in Postgres 17.

Hi,

Currently PostgreSQL reads (and writes) data files 8KB at a time.

Postgres had a preadv wrapper since version 14. This proposal used it for data files, to merge adjacent blocks into one IO. The idea was somewhat close to what Luke and Andreas were discussing in 2007: ask for several pages at once, even though their locations in shared buffers aren’t necessarily contiguous. preadv takes a list of memory buffers and fills them from a contiguous range in the file, so 16 adjacent pages can become one 128 KiB read instead of 16 reads of 8 KiB.

The beauty of read streams is that it lets the scan choose the next block through a callback. Postgres collects blocks by looking ahead, and then combines the adjacent ones up to the limit of io_combine_limit in Postgres 18.

But there’s a case where those adjacent blocks are split into multiple reads: when one page is already in shared buffers. Postgres doesn’t need to read that page from disk, so it stops reading from disk when it reaches the page that is in the buffer, and starts another read after it. From bufmgr.c:

Otherwise we already have an I/O to perform, but this block can’t be included as it is already valid. Split the I/O here.

So we want pages 0 to 15, but page 8 is cached. Instead of one read, we now have a read for pages 0 to 7, a cache hit, and another read for pages 9 to 15. We read fewer bytes, but send two requests. The worst case scenario is when you have every other page cached - now the same range needs eight separate 8 KiB reads.

Combining reads and issuing them asynchronously solve different problems. Combining reduces the number of requests while async I/O lets Postgres start a read before it needs the result, keeping other reads in flight while it processes earlier pages. This was already part of Thomas’s 2023 proposal: read streams would first provide larger synchronous reads, while giving scans an API that could later use async I/O without changing again - the infrastructure for async I/O arrived in Postgres 18

Andres Freund made a comment about this case in January 2025. He called it “the - very common - case of a bunch of “buffer misses” followed by a “buffer hit””. A month later, Thomas described the split with an example:

For example, if you ask to read 8 blocks, and the 6th one turns out to be a hit, ie already valid in the buffer pool, then we only need to read the first 5 from disk. Perhaps the 7th and 8th blocks will also need I/O, but we don’t want StartReadBuffers() to start two I/Os, so the 6th block terminates our search.

In the same email, Thomas proposed keeping those extra buffers pinned and passing them back to StartReadBuffers on the next call, that way Postgres wouldn’t have to unpin them and look them up again just because the read was split. The cached page would still break the read into separated requests, but handling the split would involve less work.

In April 2026, Andres changed how far ahead a read stream looks. Before, each hit reduced the look-ahead distance by 1, while each miss doubled it. With that rule, “a miss followed by a hit will never have the distance grow beyond 2”. In a thread about index prefetching, he also posted a WIP patch to separate two decisions previously controlled by a single internal look-ahead distance: how far ahead to issue I/O, and how far ahead to look for blocks to combine into one read.
